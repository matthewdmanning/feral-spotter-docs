instructed to perform. Follow an explicitly required reference before acting;
otherwise, do not load unrelated guidance merely because it is listed here.
Big tasks can legitimately match several rows; read each match, don't stop at the first. If you open a link that does not contain any information relevant to your task, alert the user -- include the reason you chose to open the link.

## The `docs/` submodule

`docs/` is a git submodule. It has its own branch, its own remote and its own
commit history, so a change to any file under `docs/` is **not** part of the
parent repository's working tree until the pointer moves.

Commit in this order, every time:

1. Commit inside `docs/`, on a docs branch of its own.
2. Push that branch.
3. Stage the `docs` pointer in the parent repository and commit it there.
4. Put both in the **same pull request** as the code they describe.

A parent commit that does not bump the pointer leaves the documentation
unreachable from the code. `git status` in the parent shows this only as a bare
`M docs` line, which is easy to read as an unrelated stray change and leave
behind. See [git.md](git.md).

## File Format

Project format: YYYY-MM-DD-{activity_name}
The activity_name is the name of the sprint, if one is active, or the branch, if not main. If the activity name is not known, ask the user.

Exception: `docs/adr/`, `docs/planning/`, `docs/agents/ui-ux/current-state/`, `docs/agents/ui-ux/decision-records/` are exempt — each file tracks its own last-updated date inside itself, not in the filename.
