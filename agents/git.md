# Git mechanics

Lessons about raw git/GitHub mechanics — not `gh` issue-tracker conventions (see [issue-tracker.md](issue-tracker.md) for those) and not commit/branch/PR _hygiene_ (see the global CLAUDE.md git-workflow rules for that).

## Learned the hard way

1. **GitHub squash-merge takes its subject from the PR title, not from any commit message on the branch.** Fixing a commit subject via force-push does not fix what lands on the base branch. Fix the PR title too, before merging.
2. **A commitlint workflow triggered on both `push:` and `pull_request:` lints different commit ranges.** The `push`-event run isn't scoped to the PR base and can re-lint already-merged ancestor commits from other branches, producing a failure unrelated to the current PR.
3. **When `gh pr checks` shows the same check name both passing and failing on one head SHA, they're different workflow runs from different trigger events.** Compare `gh run view <id> --json event` before treating either as authoritative.
4. **`git rev-parse <ref>` without `--verify` doesn't fail on an unresolvable ref — it echoes the argument back verbatim** (its "look like a flag" fallback, meant for argument-parsing scripts). A bare `git rev-parse MERGE_HEAD` inside a hook silently returns the literal string `MERGE_HEAD` instead of empty/erroring when there's nothing to merge-resolve. Always use `git rev-parse --verify -q <ref>` when the ref might not exist.
5. **`MERGE_HEAD` is not guaranteed to exist on disk (or resolve as a ref) inside `pre-merge-commit`, for a clean auto-committing `git merge <ref>` with no conflicts** (confirmed on git 2.45.1/Windows) — it only gets persisted when the merge stops before committing (conflicts, or `--no-commit`). A hook that needs to inspect the incoming branch during a clean merge has no reliable on-disk signal at that point; `pre-commit` doesn't fire for merge auto-commits either. Block the command at the agent/tool layer instead (a PreToolUse hook on the shell command string), not via a git hook that inspects merge state.
6. **`git reset --hard <commit>` rewrites every tracked file to match that commit, not just files the current branch differs on.** If an unrelated uncommitted change (e.g. a pending deletion) happens to be identical-at-HEAD across branches, a reset done for a completely different reason (undoing a test merge, backing out an experiment) silently discards it too. Check `git status` for uncommitted changes unrelated to the reset's purpose before running it, not just the ones you're trying to undo.
7. **A push runs a prettier gate, and it blocks the push rather than fixing it for you.** `npm install` runs `prepare`, which sets `core.hooksPath .githooks`. `.githooks/pre-push` runs `node scripts/format-changed.mjs --fail-on-change` over the files the branch changed against `origin/main` (`PRETTIER_BASE` overrides the base). Prettier rewrites them in place, so a blocked push leaves a dirty tree: commit that result and push again. The gate covers `.ts/.tsx/.js/.jsx/.json/.md/.yml` only — it never reads a `.kt`, `.swift` or `.gradle` file, so passing it says nothing about native code. Run `npm run format:check` before pushing to see the verdict without the rewrite. **Never skip the hook** — a `PreToolUse` hook denies the skip flag outright, and the gate is not the thing that is wrong.

8. **The gate used to fail on an unrelated dirty file, and no longer does.** It once ended with a bare `git diff --quiet`, which fires on _any_ dirty working tree at push time, not just the files the hook reformatted. Commit `bebc5f7` replaced it with `--fail-on-change`, scoped to the files the script was given. If that symptom appears again, the hook has been reverted — fix the hook, do not stash around it.

9. **`docs/` is a submodule, so its commits and the parent's pointer are two commits that must travel together.** The order is fixed: commit inside `docs/` on a docs branch of its own, push that branch, then stage and commit the `docs` pointer in the parent repository, and put both in the same pull request as the code. Two ways this goes wrong. A parent commit that skips the pointer bump leaves the documentation unreachable from the code — and the parent's `git status` shows the pending bump only as a bare `M docs` line, which reads like an unrelated stray change and gets left behind. Conversely, a `git checkout` or `git reset` in the parent moves the pointer and can detach or rewind the submodule's HEAD without saying so, so run `git -C docs branch --show-current` after any parent-branch change and before committing anything inside `docs/`.
